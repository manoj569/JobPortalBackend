# Workday production hardening audit

2026-10-11. Audit completed before new hardening implementation. The preceding local reconciliation changes and existing untracked artifacts are preserved. No production reads beyond the previously unauthorized admin GET (401), no production database connection, import, activation or write.

## Verified mechanisms and failures

- Workday gathers the entire listing, then fetches detail batches with a bounded two-batch channel, request pacing, adaptive concurrency, finite retries, response size guards and a default 1800-second provider budget. Listing totals, unique paths/IDs, placeholders, repeated pages, anchor changes and detail failures gate native completeness. No upstream version token is provided by the supported CXS contract.
- PwC's supplied `RunBudgetExceeded` after about 30 minutes matches that explicit budget. Exhausting it cancels the provider independently of the runner token, reaches the provider/infrastructure failure path and prevents reconciliation. Why requests consumed that duration (HTTP latency, throttling, database time, deployed settings) is unverified without production telemetry. It is not proven to be an HTTP concurrency defect.
- The runner persists bounded creations before final reconciliation, so Accenture's host shutdown can retain committed jobs. The durable worker records interruption; expired leases recover under the same distributed source lock. However, there is no durable listing identity, processing cursor or item receipt. Retries replay listing/details from zero; the three-attempt cap is suitable for failures but cannot represent dozens of healthy continuation slices. A shutdown after commit but before heartbeat can also leave counters behind durable data.
- Scheduled execution bypasses the durable queue and directly invokes a scoped runner. The single durable hosted worker processes one source to completion before polling another. Scheduler concurrency settings therefore do not bound/parallelize queued work, and long sources delay other queued companies.
- PTC: the prior local tests demonstrate a completeness propagation defect: selected snapshot completeness was cleared by any geography-review decision, while native `ScanComplete` remained true. Full observed IDs already include geography exclusions and are the reconciliation authority. Geography is not evidence of absence. A positive configured test cap, missing identities or other guard can also produce the same historical failure. The historical run's DiagnosticsJson remains unverified after GET 401; do not claim its exact guard has been proven. The local generic correction and explicit guard diagnostics are preserved.
- Source-scoped identities and canonical URL uniqueness, local/distributed source guards, ordered cross-provider creation locks, bounded batch preload and atomic EF SaveChanges already prevent duplicate creations. They must remain intact. Publication still delegates to the current JobService authority, and category is optional. The current repository policy intentionally does not gate imported publication on the legacy AutoPublishEnabled/rights metadata; this task preserves that behavior rather than inventing approvals.
- Workday listing `locationsText` is a display label, not an authoritative exhaustive set of hiring locations. Details may add locations/country contradictions. Safe early rejection cannot be inferred from a lone foreign label or Remote. Supported listing metadata does not establish all locations; details remain required until a reliable exhaustive contract exists.
- Category resolution logs SourceMappingMissing per unclassified item; positive category existence is cached, but diagnostic logging needs run aggregation. Publication/reconciliation cancellation and per-record isolation already exist.

## Smallest robust extension

Use the existing run row and source locks. Add durable checkpoint JSON, bounded execution count, additive run states, and a per-item receipt journal. Stage persistence receipts inside existing job SaveChanges under the existing creation locks. Stage successful publication receipts before the existing JobService publication save. Reuse receipts when recovering an unacknowledged batch; never manufacture Created counts or publish twice. Advance the cursor only after data/publication outcomes are committed. Retain lean observed geography/identity facts and a full listing fingerprint; re-read and compare the supported listing on continuation. Changed/unsafe snapshots terminate without closure; normal fresh queued/scheduled scans rebuild from zero. Healthy continuation slices do not exhaust fault retries; no-progress crashes and total executions remain bounded.

Route scheduled production work through the existing queue, provide configurable finite detail-work/time slices, and apply the source-concurrency setting to worker loops. Preserve rate limits, SSRF, stable identities, source configuration, India rules, categories, deduplication, quality/public visibility and source-scoped absence reconciliation. Add structured continuation diagnostics and aggregate category warnings.

An additive EF PostgreSQL migration is essential for durable state and exact replay receipts. No production migration is executed. Acceptance testing must include 5000+ vacancies, crash windows, shutdown/budget recovery, real PostgreSQL fencing/transactions, fairness, publication and Discover visibility. Production readiness must not be claimed before those tests pass. Existing test-harness analyzer failures (184 diagnostics in the preceding verified baseline) remain separate from normal Release API builds.
