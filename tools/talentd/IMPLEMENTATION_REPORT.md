Read-only status uses persisted runs/receipts. No second ingestion or publication mechanism.

4. **Migration:** `20261016100020_AddTalentdAcquisitionSource`, scaffolded with `dotnet ef migrations add` using the PostgreSQL project/factory. Source-data-only migration; no added tables/columns and no model snapshot delta. Updates one existing active/soft-deleted Talentd registration or inserts if absent, safe on repetition. Down disables Talentd without deleting referenced source/jobs/receipts. Not applied to production or any database during this task.
5. **AcquisitionSource:** ProviderKey `talentd`, Name `Talentd`, IsEnabled=true, AutoPublishEnabled=true, IsDeleted=false. New-source Id `7fb8c010-f683-481b-b98f-71e45717f987`; existing source Id preserved. Website and SerpApi configurations unchanged.
6. **Policy:** explicit allowlist `website-crawler` / `talentd` in bulk eligibility, final ingestion boundary, automatic publication and JobService publication. Other providers retain their existing gates. Talentd keeps technical title/identity/URL/format/persistence limits, requires stable ExternalJobId and safe DiscoveredUrl, rejects unsafe supplied application/canonical URLs, and does not require optional business fields, location evidence, confidence, employer verification or a known ATS. Talentd receipt eligibility is ContentNeutral.
7. **Publication:** Talentd requires available/enabled automatic publication even when metadata omits autoPublishRequired. Each committed job/receipt is followed by existing publication service; successful receipts are Published with NULL error and count toward durable PublishedCount. Published updates return AlreadyPublished. Required publication that cannot finish stays pending/recoverable. Existing editorial suppression and publication ownership protections remain. Public visibility/expiry queries use the same explicit Talentd/website content-neutral exception; source deadlines remain stored as evidence.
8. **Existing persisted fields:** title, company identity, display location, explicit country evidence, recognized employment/workplace enums, experience range, skills, posting/deadline/observation dates, description, category when resolved, three separate URLs, source identity and metadata. See FIELD_AUDIT.md for every requested field and A/B/C/D classification.
9. **Newly wired:** explicit JSON-LD salary range/currency/period; degree/education text to existing EducationRequirement; responsibilities to Responsibilities; qualifications to Requirements; benefits to Benefits; missing company logo; complete original Talentd evidence; additive skill refresh. No new candidate DTO properties, so existing payload fingerprints are unaffected.
10. **Not separately structured:** batch years, fresher boolean, original salary text, source UpdatedAt, separate city/state/country columns, unsupported/multi-valued employment, rich education objects, eligibility prose and arbitrary source sections. All remain in `Job.SourceMetadataJson.discovery.extracted.talentd`; location display uses existing DTO fields. Worker occupational categories remain metadata where no exact taxonomy mapping is supplied. No schema bloat or guessed new taxonomy.
11. **Salary:** uses explicit numeric baseSalary.value facts (including scalar value), explicit three-letter currency and YEAR/MONTH/HOUR period. No text parsing, currency guessing or annual conversions were added. Original salary text/evidence retained. Existing classification/admin override rules remain.
12. **Skills:** existing Skill/JobSkill relations, whitespace/case normalization and duplicate suppression; no description-based extraction. Talentd refresh adds newly supplied skills without clearing reviewed associations when optional evidence is missing.
13. **Batch years:** exact source array retained in metadata; no existing structured relation was found.
14. **Education:** scalar/array text or raw degree fallback uses existing 200-character EducationRequirement. Objects/long text remain complete in metadata rather than truncating them into the column.
15. **Company logo:** safe public URL of at most 2048 characters; conditional database update fills only NULL/empty LogoUrl. It cannot overwrite a trusted value, including a concurrent administrator edit. No remote logo download or verification dependency.
16. **Description:** existing HTML-to-plain-text normalization suppresses script/style and preserves useful content. Talentd removes the acquisition-only 16,000-character description gate because Job.Description is text; request-size and other field limits remain. Metadata retains original source evidence as JSON, never rendered as executable markup.
17. **URLs:** DiscoveredUrl stays Talentd detail; CanonicalJobUrl stays worker employer/ATS URL; ApplyUrl is first choice for Job.ApplicationUrl. Original safe URLs also persist in receipts. No ATS allowlist and no replacement of a valid direct application link with the Talentd page.
18. **Identity/upsert:** source Id + normalized deterministic acquisition ExternalJobId wins; distinct explicit Talentd identities do not merge on title/company/location/application similarity. Existing request fingerprints, advisory locks, per-item commit and durable replay mechanisms remain. Same ImportId with changed payload is rejected; same payload replays durable indexed receipts.
19. **Reconciliation:** `GET /api/internal/v1/jobs/bulk-import/status?sourceType=talentd&importId=<URL-encoded ImportId>`. ImportId maps to durable BatchId. 404 gives NOT_FOUND; 200 gives IN_PROGRESS (including AwaitingPublication), COMPLETED, or persisted FAILED. Response has ImportId, BatchId, RunId, Status, all requested summary counters, FailureSummary, and completed `receipt` in the approved worker bulk response shape including indexed item JobIds. Running counters are the currently persisted run snapshot, not a claim of final totals. Worker automatic polling was not changed; operator reconciliation instructions are prepared.
20. **Status authentication:** same controller-level FresherServiceTokenFilter, request limits and rate limiter as POST; configured >=32-byte Bearer service token with constant-time comparison. Missing/invalid token fails closed; unconfigured token returns 503. Read queries use AsNoTracking and do not save, lock, resume or otherwise mutate runs.
21. **97-second evidence:** exact root cause is not established without production phase/DB timings. Code inspection shows sequential company/domain/name/owner queries, duplicate checks before and under creation locks, skill lookup, per-item advisory locks/transaction/save, receipt lookup/persistence, and publication fetch/validation/save plus receipt status save. Network/database round trips are a plausible contributor; no new external HTTP calls were introduced. No production benchmark was run.

Per-item durability/transactions, failure isolation and exact receipt semantics retained. No blanket timeout increase or giant transaction.
